# Claude instructions: research only

Read `NETWORKING_CONTEXT.md` together with this document. This pair is the complete instruction packet; do not require Codex's document or archived plans.

## Role and schedule

Claude owns **profile research and company-email finding**. Email finding runs through `Networking Workflow/find_work_email.py`, a cascading lookup (Prospeo → Hunter → GetProspect → Tomba → MineLead, first verified hit wins, with local caching so the same person is never re-queried at the same freshness). Apollo is not part of this workflow and must not be used.

Run this workflow **twice daily** on the PC scheduler — a good default is **3:00 a.m. and 6:00 a.m. Eastern**, including weekends, each run independent and self-contained (a fresh session with no memory of the other run). Aim for roughly **5 qualified candidates with verified company emails per run**, so the two runs together build a healthy daily pool, rather than 12–15 in a single run. Each run must re-read both instruction documents and the most recent handoff(s) — including one published earlier the same day — to rotate firm/city coverage and avoid duplicating a parent bank/group the other run already used that day; if a same-day handoff already exists, publish with a distinguishing suffix (e.g. `YYYY-MM-DD-claude-research-2.json`) rather than overwriting it. Codex sends only Monday–Thursday, up to 10 initial emails per day. If the PC is asleep, LinkedIn access is unavailable, the finder script fails, or the run cannot finish, report the failure; the scheduled start alone does not count as a completed handoff.

**Browser selection (unattended runs).** If more than one browser is connected for this account, resolve the target browser programmatically at the start of every run (e.g. match on OS platform for the campaign's locked-in device) rather than prompting — an unattended run has no one to answer a picker. Stop and report the specific blocker if the intended browser is not connected; never silently fall back to a different one.

The campaign is Summer 2028 U.S. Investment Banking Summer Analyst recruiting. Use the 40-firm list embedded in `NETWORKING_CONTEXT.md`. New York and Chicago are primary; San Francisco, Houston, and Philadelphia are secondary. Aim for roughly 80% New York/Chicago across sends when qualified people support that mix. Rotate firms over runs, with BB/large-platform and middle-market banks ahead of selective elite boutiques.

## Steps for each run

1. **Check the campaign and existing records.** Confirm the target send date, current class/campaign details, and firm list. Read recent handoffs to rotate toward firms and cities searched less often, including firms that yielded no candidates. Read both `Trackers/Outreach Tracker.xlsx` (prospects, sends, unanswered threads, suppression) and `Trackers/Recruiting Tracker.xlsx` (responders and relationship history) to avoid known contacts and active threads. Absence from the main tracker does not mean someone has never been emailed. Claude may read both trackers but must not edit either. If Gmail history is accessible, use it as another read-only duplicate screen. Codex makes the final duplicate decision later.
2. **Search LinkedIn manually.** Use focused searches and inspect profiles one by one in the authenticated browser. Search Analysts and Associates first; consider VPs and MDs for a strong shared connection or specific senior-level question. Include advisory/M&A, restructuring, industry coverage, and ECM/DCM only when the team is within investment banking. Exclude Sales & Trading, Prime Services, research, asset/wealth management, and non-IB corporate/commercial banking. Do not scrape, export result pages, auto-page, or send LinkedIn messages.
3. **Verify each candidate.** Confirm current firm, title, IB role, city, and group from the profile or another reliable source. **Only include people already working full-time.** Exclude current students, incoming/not-yet-started analysts (e.g. "Incoming Analyst," a start date in the future), and anyone whose most recent listed role is a summer analyst/internship rather than a started full-time position — a completed prior summer-analyst stint at the same or another firm is fine context, but the person must currently be in a real full-time seat. Map Greenhill to parent Mizuho and Miller Buckfire/Capital Structure Advisory to parent Stifel. Record the actual office; a firm's city presence does not prove where the person works. If the group remains unclear, mark `group_status: "unverified"` and keep the person as a lower-priority research candidate. While on the profile, also capture whatever the candidate's own page actually states — undergraduate school, fraternity/sorority or other org affiliations, hometown, and listed interests/activities (About section, volunteering, skills) — plus the exact profile URL for `linkedin_url`. Never infer a major, fraternity, hometown, school, interest, or group; if the profile doesn't state it, leave it blank rather than guessing. This captured detail feeds Step 5's connection-strength ranking below.
4. **Find and verify the company email with the finder script.** Run `find_work_email.py` against the verified LinkedIn identity, current bank, and office, using its cascading provider order — do not call any provider API directly, and do not construct or guess an address. Include a company address only when the script returns a **verified** result; record the address, the provider name it actually resolved through (e.g. `Prospeo`, `Hunter`, `GetProspect`, `Tomba`, `MineLead`) as `email_source`, and the Eastern verification timestamp in the handoff. MineLead's `/find` only returns a 0–100 quality score, not a pass/fail verification flag — treat a MineLead hit as `email_verification_state: "unverified"` and hold it to the same rejection standard as any other unverified address. Reject guessed patterns, personal addresses, catch-all, unknown, ambiguous, unverified, or stale records. Keep profiles without a verified address out of the `READY` candidate list and report the resulting shortfall. Recheck a carried-forward person's email verification when refreshing the pool, since the cache only skips a *repeat* lookup, not a stale one past a reasonable freshness window. Claude does not write either tracker. Mind each provider's monthly free-tier ceiling (Prospeo 100, Hunter 50, GetProspect 50, Tomba 25, MineLead 24) now that this runs twice a day instead of once — a later run in the day may have less quota left.
5. **Rank and write a useful reason.** Same major, fraternity, or hometown is the strongest common ground; same school is next; shared interests are weaker. A strong IB team and office fit may qualify without common ground. Give a specific reason Codex can use in an email, tied to a source. Order candidates from strongest to weakest fit using `priority_rank` starting at 1. No generic “works at target bank” entries.
6. **Apply a provisional group screen.** Avoid more than one proposed person per parent bank and IB group in the same handoff unless clearly labeled as alternatives. For an unverified group, avoid adding another person at that parent bank. Codex will apply the final cross-week and cross-city cap using the tracker and Gmail.
7. **Produce a dated handoff.** Aim for **12–15 qualified candidates with verified company emails available for the next send day**, giving Codex alternatives for a 10-email batch. Research every day; refresh and carry forward eligible unsent people rather than requiring 12–15 entirely new people each day. Record the true count and any shortfall. Write one UTF-8 JSON file at `Networking Handoffs/YYYY-MM-DD-claude-research.json`, where the filename date is now the **research date** in America/New_York. Set `send_date_et` to the next Monday–Thursday after the research run. Thursday, Friday, Saturday, and Sunday files therefore target Monday; Sunday's file must include refreshed, eligible carryovers from earlier research. Build and validate the complete JSON in a temporary file in the same folder, then publish it by renaming as the last step. Use `READY` when at least one qualified candidate with a verified company email is present; use `BLOCKED`, zero candidates, and a specific reason when none can be provided. Do not modify a published handoff that Codex has started consuming.

## Completion and failure

A successful research run has parseable schema-version-2 JSON, `status: "READY"`, at least one candidate with a verified company email from the cascading finder, matching count, unique ranks, LinkedIn URLs and company emails, populated `search_coverage`, required fields, and the next Monday–Thursday send date. A `BLOCKED` handoff communicates an access failure or zero qualifying people and intentionally prevents Codex sends; it still records any searches that were completed. If fewer than 12 qualify, report the actual count; do not fabricate profiles or addresses. Claude does not send emails or modify either tracker.
