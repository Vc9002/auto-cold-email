Read `NETWORKING_CONTEXT.md` together with this document. This pair is the complete instruction packet for a daily run; do not require Codex's document, `SETUP_STATUS_2026-09-26.md`, or archived plans — those are history, not daily-run steps.

## Role and schedule

Claude owns **profile research and company-email finding**. Email finding runs through `Networking Workflow/find_work_email.py`, a cascading lookup (Prospeo → Hunter → GetProspect → Tomba → MineLead). Run this workflow **twice daily, at 3:00 a.m. and 6:00 a.m. Eastern**, including weekends, as two independent scheduled runs each starting from a blank session. If the PC is asleep, LinkedIn access is unavailable, the finder script fails, or the run cannot finish, report the failure and stop; the scheduled start alone does not count as a completed run.

The campaign is Summer 2028 U.S. Investment Banking Summer Analyst recruiting. Use the 40-firm list embedded in `NETWORKING_CONTEXT.md`. New York and Chicago are primary; San Francisco, Houston, and Philadelphia are secondary. Rotate firms using `search_coverage_cumulative.not_yet_searched` in the pool file (below) — always pull from that list before re-searching an already-covered firm.

## The pool file replaces dated handoffs

There is **one file**, `Networking Handoffs/research_pool.json`. Every run reads it, updates it in place, and writes it back — never publish a new dated snapshot file. This removes the collision-safe-publish problem entirely (no more `-2`, `-3` files fragmenting one day's candidates across separate documents) and lets Codex always see every verified candidate that hasn't been sent yet, not just today's output.

Each candidate row has a `status`:
- `READY` — verified company email, ranked, available for Codex to send. Give it the next unused `priority_rank` (lowest number = highest priority; keep ranks unique across the whole pool, not just this run).
- `PENDING_EMAIL` — profile verified, no verified email yet. Re-attempt the finder script on a future run; after 3 failed attempts on the same domain, add a note recommending the person be reverified for current employment or excluded.
- `PENDING_CATCHALL_RECHECK` — the domain returned `accept_all`; see the catch-all rule in `NETWORKING_CONTEXT.md`. Re-run the finder script and promote to `READY` only if 2+ providers independently return the identical address.
- `EXCLUDED` — will never be READY (departed, non-IB role, opted out, duplicate). Keep the row for history; never delete rows.
- `SENT` — Codex has sent to them. Claude does not edit `SENT` rows.

## Steps for each run

1. **Load the pool file and both trackers, read-only.** Read `Networking Handoffs/research_pool.json` first — this is now your primary duplicate/coverage check and is far smaller than the full trackers. Then read `Networking Handoffs/tracker_digest.json` (Codex regenerates it after every send run) for send/reply history and bank/group cooldowns. **If the digest does not exist yet or is older than Codex's most recent send, read `Trackers/Outreach Tracker.xlsx` and `Trackers/Recruiting Tracker.xlsx` directly instead** — the pool only knows about people Claude researched, not every prior contact. Claude may read both trackers but must not edit either.
2. **Search LinkedIn manually.** Use focused searches in the authenticated browser, prioritizing firms in `search_coverage_cumulative.not_yet_searched`. Search Analysts and Associates first. Include advisory/M&A, restructuring, industry coverage, and ECM/DCM only within IB divisions. Exclude Sales & Trading, Prime Services, research, asset/wealth management, and non-IB corporate/commercial banking. Do not scrape, export result pages, auto-page, or send LinkedIn messages.
3. **Find the email before doing a deep profile read.** For each name+firm found in search results, run `find_work_email.py` first. Only open the full LinkedIn profile (mutual connections, education dates, group history) for people who come back `verified` or `accept_all`. Skip a deep profile read for anyone the finder script returns `not_found` on the first attempt — log them at `PENDING_EMAIL` with just name/firm/city and move on. This is the single biggest token saver in this workflow: roughly half of candidates fail at the email step, and a full profile read is far more expensive than one finder-script call.
4. **Verify each candidate that has an email lead.** Confirm current firm, title, IB role, city, and group from the profile. Map Greenhill to parent Mizuho and Miller Buckfire/Capital Structure Advisory to parent Stifel. If the group is unclear, mark `group_status: "unverified"` and still include the person — an unverified group is not a reason to exclude, only a reason to cap that parent bank at one active prospect. Never infer a major, fraternity, hometown, school, interest, or group.
5. **Apply the catch-all rule.** If the finder script returns an unverified address on a catch-all domain, do not discard the candidate. The normal lookup stops at the first provider and caches the answer, so re-running it can never produce a second opinion. Instead run the recheck mode, which asks every provider and reports agreement: `python find_work_email.py First Last --domain example.com --company "Firm" --all-providers`. Use its `suggested_email_verification_state` as-is; never call provider APIs by hand or upgrade the state yourself. It costs up to one credit per provider, so use it only on catch-all candidates and `PENDING_CATCHALL_RECHECK` rows. If 2+ providers agree on the identical address, mark `email_verification_state: "accept_all_2plus_agree"` and set `status: "READY"`. If only one provider returns an address, or providers disagree, set `status: "PENDING_CATCHALL_RECHECK"` and move on.
6. **Rank and write a useful reason.** Same major, fraternity, or hometown is the strongest common ground; same school is next; shared interests are weaker. Give a specific reason Codex can use in an email, tied to a source. New `READY` candidates get the next unused `priority_rank` in the pool (append after the highest existing rank; never renumber existing `READY` rows).
7. **Apply the one-per-bank-and-group cap across the whole pool**, not just this run's new candidates — check existing `READY`/`SENT` rows for the same `parent_bank` + `ib_group` before adding a new one.
8. **Update the pool file safely.** Work on a copy named uniquely for this run (e.g. `Networking Handoffs/.tmp-pool-<YYYYMMDD-HHMMSS>.json`), never on the live file. Add new rows, and update existing `PENDING_*` rows in place (new email lead, new status, updated `notes`). Update `last_updated_et`, `last_updated_by`, and `search_coverage_cumulative` (move firms from `not_yet_searched` to `searched` as you cover them, and reset the list back to all 40 firms once every firm has been searched at least once). Never touch `SENT` rows. Never delete a row. Give every row you add or touch a `profile_checked_at_et`. Before publishing, run `python "Networking Workflow/outreach_preflight.py" --validate-pool <your temp copy>` and fix anything it reports. **Then, immediately before replacing the live file, re-read `research_pool.json`: if its `last_updated_et` changed since you loaded it (another research run or Codex wrote in the meantime), re-apply only your own additions and edits onto that fresh copy, validate again, and then replace** — never write back a stale copy, because that silently erases the other writer's rows, including Codex's `SENT` markers. Delete your temp copy afterward.

## Completion and failure

A successful run updates the pool file with at least one new or promoted candidate, or explicitly reports zero progress and why (e.g. every searched profile lacked a verifiable email). Report: how many `READY` candidates now exist in the pool overall, how many are new this run, which firms were searched, and any material gap. Claude does not send emails or modify either tracker.
